v0.6.0 (2026-10-05) — a trash can on the map
- a bin in the map's bottom-left corner. Drag a node onto it to take that
  session off the board; if the session is still running, it is ended too
- dropping is decided from where the pointer is, not where the node's box
  overlaps: a 172px node dragged near the corner covers the bin long before
  the hand is anywhere near it. The drop zone is the 46px icon plus 14px of
  margin, which is what makes it hittable at all
- a live session gets a native confirm naming it and its pid, and the detail
  line says what is actually lost: the turn in flight, not the transcript,
  which stays on disk and resumable
- the pid is read back out of the process table immediately before the signal
  and has to still look like a claude session (same test the collector uses).
  A pid the last poll saw can belong to something else two seconds later, and
  nothing is signalled unless it still matches
- SIGTERM, never SIGKILL, so claude writes its transcript out on the way down.
  The handler waits 600ms and reports whether the process actually went, since
  one wedged in a syscall can sit on a SIGTERM and the map should not claim it
  is gone
- a binned session is held off the map for 8s, or until a snapshot agrees its
  pid has cleared, whichever comes first. Without the hold the node springs
  back for a poll after being thrown away; with an expiry, one that survived
  the signal reappears instead of vanishing for good
- cancelling puts the node back where the drag started, rather than leaving it
  parked on top of the bin where it was dropped
- the bin is pointer-events: none, so a node sitting over it stays grabbable
- SB_TEST_TRASH="<title substring>" drives the whole drag through the real
  pointer handlers. The kill is refused while it is set, so the test exercises
  the gesture, the pid re-check and the board cleanup without ending anything.
  It opens the panel first: the board starts on the rail, where there is no map
- map subtitle now mentions the bin; it had no other way to be discovered

v0.10.0 (2026-10-13): context and token-use counters per worker
- every assistant turn in a transcript already carries the API's own `usage`
  block (input/output/cache token counts); collector.js now reads it instead
  of leaving it on the floor
- contextTokens: the newest turn's input + cache_creation + cache_read, which
  is exactly the size of what was last sent as the prompt, i.e. how full the
  context window is right now. Comes nearly free: it's read off the same
  backward walk through the tail that already finds title/cwd/turn, no extra
  I/O. Computed for every tracked session, closed ones included, since it
  costs nothing extra once that walk is already happening
- totalTokens: every turn's prompt-plus-reply summed over the session's whole
  life, the same way Claude Code's own cost accounting counts it (cache reuse
  billed, and counted, every time it's resent, not once). This one isn't free:
  a transcript runs to tens of MB, so summing it fresh every 2-second poll was
  never an option. Each file keeps its own cursor (scanUsage() in
  collector.js) of bytes already turned into a running total plus whatever
  undecoded tail didn't yet end on a newline, so a poll only ever reads what
  was appended since the last one. Scoped to live sessions only (has a pid):
  the first time a session is seen live costs one full-file read, a closed
  session's total will never change again and isn't worth paying that to learn
- shown as "142K ctx · 310M total" (fmtTokens()/tokenLine() in index.html):
  list row meta, the office's ball tooltips and "others"/lead chat-head
  titles, and the map node's own title attribute (no room for a third printed
  line in a 172x60 node, so it rides the tooltip the port's title already
  used that same way)
- deliberately not a dollar figure: pricing varies by model and tier and a
  hardcoded table would go stale and mislead. The raw token counts are honest
  about what they are; a session that looks alarming at "150M total" is
  mostly cheap cache re-reads billed at a fraction of fresh-input price, not
  150M tokens of fresh processing, and this doesn't try to tell them apart

v0.11.0 (2026-10-15): the board's own calls pick a model, log their cost, and chat stops replaying transcripts
- consult, relay and chat never passed --model, so they ran on whatever the
  user's default was. With Opus 5.5 as the default, every "ask it" click cost
  ~36x what Haiku charges for the same answer (measured: $0.066 vs $0.0018 for
  a one-word reply). A JOBS table in main.js now names the model per job:
  consult and relay run on Haiku at --effort low, chat runs on Sonnet
- every call also passes --tools Read,Grep,Glob. Each tool definition rides in
  the prompt, and narrowing to the read-only three took a call's fixed cost
  from ~17K tokens to ~6K. These run under -p with no permission mode, so the
  write tools were being refused anyway
- --bare was tried and rejected: it skips keychain reads, so on a subscription
  login it fails before reaching the API (comes back with zero usage)
- all three now go through one runJob() with --output-format json, which
  appends a line per call to usage.jsonl in the app data dir (job, model,
  input/cache/output tokens, dollars, ms, prompt size, resumed or not), and
  shows "haiku · 7K tok · $0.0008" beside each answer in the list, the map's
  composer and the office chat
- chat no longer does --resume --fork-session on the lead. The first message
  starts a fresh process seeded with the same bounded digest() excerpt consult
  uses; later messages resume that small conversation. A follow-up now costs
  what the chat has grown to, not what the lead's whole history weighs
- total_cost_usd on a resumed session is the running total for the whole
  conversation, not that call's share; found by the usage log on the first
  test run (message two reported $0.0149 when its own share was ~$0.0007).
  Each conversation's last total is remembered and only the difference charged
- office chat header gets a model button (sonnet -> opus -> haiku), remembered
  across restarts; switching mid-chat resumes the same conversation on the new
  model. main validates it against the same three aliases as hiring and falls
  back to the job's default for anything else
- SB_USERDATA overrides the userData dir, so a test copy runs beside the
  installed board instead of standing down to its single-instance lock
- tested end to end through the real app's IPC with playwright _electron:
  consult, chat (message two recalled a codeword from message one, on a

  300-530K, which is where the spend actually went

  same directory, on the same model tier, named "<title> cont", with a first

  The old session is left running; ending it stays a separate, deliberate act

v0.14.0 (2026-10-15): a usage panel, and two counting bugs it exposed
- new "usage" button (list/map footer, and the office strip's empty slot)
  opens an overlay over whichever view is open: a headline API-equivalent
  dollar total, tokens / turns / sessions, and bar lists by model, by project
  and by most expensive session, for today / 7 days / 30 days / all
- dollars are what the tokens would cost at per-token API prices (src/usage.js
  PRICES, from the claude-api model reference cached 2026-10-06; cache writes
  1.25x input for 5m, 2x for 1h, using each response's own TTL split). On a
  subscription that isn't the bill, and the panel says so; it is the fair way
  to compare sessions. The formula reproduces two costs the CLI reported
  exactly ($0.0657692 Opus 5.5, $0.00076723 Haiku 5.5). Haiku 5.5's 5x rate
  above 100K-token prompts is applied; Opus 5's cache-read rate isn't in the
  reference, so it uses the standard 0.1x
- bug 1, in the v0.10.0 per-session total: one API response is written once
  per content block, every copy carrying the full usage, so totals counted
  most turns 2-5 times (168 usage lines for 70 responses in one session).
  Copies are always consecutive (0 exceptions in 11,784 lines machine-wide),
  so scanUsage() now skips a repeat of the previous message id

2026-10-24  v0.17.0  dock a session's terminal in the office

- the office's middle slot can hold one session's real Terminal window. When the
  office opens, it takes the session that was opened first (registry startedAt,
  or ps etime for sessions found by the process scan). Dropping a ball on the
  slot swaps that session in; the one it replaces goes back where it was. The
  "chat" button on the slot's bar sends the window home and shows the chat.
  When the docked session ends, the next oldest takes its place
- how: a window cannot be reparented into Electron, so the slot is a hole. The
  panel stops painting its background and the hole paints it back around
  itself (z-index -1 plus a large box-shadow, clipped by the panel's rounded
  overflow). main.js moves the Terminal window, found by tty, to sit exactly
  under it and follows board moves and resizes. Clicks over the hole fall
  through via setIgnoreMouseEvents(forward), decided by elementFromPoint so a
  popover over the hole keeps its own clicks
- docking raises the window and activates Terminal: the hole shows whatever is
  under the board, so another app's window in between would take the clicks
- every dock change runs through one queue, and each window's original bounds
  are kept for the life of the board. A Haiku review found that concurrent
  docks could strand a window in the slot or record the slot as its home, and
  that a snap throwing mid-undock left the window never following again
- quitting puts the docked window back (tested: docked, quit, back at its
  original bounds). Tile and put-away leave the docked window alone
- trap: `before` is reserved in AppleScript, and a variable named that is a
  syntax error that makes the dock fail
- the chat panel is gone: the middle slot is always the dock. The boxes for the
  other live sessions and the recent closed ones, and the hand off button, moved
  above the docked terminal. Clicking a ball or a box now docks that session
  instead of picking a chat lead, and put away keeps the docked window up. With
  nothing docked, the slot shows "drop a session here". main.js's chat handler
  and jobs.js's chat job are now unused by the page; left for now
- closed-session boxes removed from the office (and with them drag-to-floor to
  reopen; the list's "recent" section still reopens)
- a docked window dragged out and dropped back now snaps in. Terminal reports
  no drag, so main.js reads the docked window's bounds every 900ms; a window
  that has stopped moving with its centre inside the slot is snapped back,
  anywhere else it counts as pulled out: the slot shows the board again with
  "pulled out · drag its window back here, or click its ball", and the board
  stops following it on moves or restoring it on quit. Clicking its ball docks
  it again. The watcher holds off 1.5s after any board move so a window still
  catching up is not mistaken for one pulled out. The slot is now a wrapper
  that keeps its size whichever face shows, so the rectangle is always known.
  Tested by script: pulled out -> placeholder shown, dropped back ~50px off ->
  snapped to the exact slot bounds
- the docked window keeps up with a board drag. Each follow step used to be a
  fresh osascript walking every tab for the tty, ~140ms (measured; ~95ms of it
  starting the process). Now one osascript stays open for the board's life, a
  JXA loop taking "id x y w h" on stdin and moving the window by id: ~16ms a
  move. Moves asked for while one is in flight collapse into the next, which
  reads the board's latest position. A stale window id falls back to the tty
  search once and keeps the new id. The JXA is inline (osascript -e) since the
  packaged app's src is inside an asar osascript cannot read
- measured with a scripted 40-step drag (8px per 16ms): the terminal held its
  offset from the board on 33 of 40 samples, at most ~5 steps behind on the
  rest, and settled exactly
